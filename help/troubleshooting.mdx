Most CryptoMCP problems fall into a small number of categories: the server won't start, the AI client can't connect, a tool returns an unexpected error, or data looks wrong. Work through the relevant section below to pinpoint and fix your issue. If a problem persists after following these steps, enable debug logging (set `LOG_LEVEL=debug` in your `.env`) and check the server output for more detail.

---

## Server Won't Start

<Accordion title="Missing or invalid .env file">

CryptoMCP exits at startup if required environment variables are absent. The error message will name the missing variable, for example:

```
Error: Missing required environment variable: COINGECKO_API_KEY
```

**Fix:**

1. Confirm that a `.env` file exists in the project root (not in a subdirectory):
   ```bash
   ls -la .env
   ```
2. If the file is missing, copy the example:
   ```bash
   cp .env.example .env
   ```
3. Open `.env` and make sure `COINGECKO_API_KEY` and `ETHERSCAN_API_KEY` are set to real values, not the placeholder text from `.env.example`.
4. Restart the server.

</Accordion>

<Accordion title="Wrong Node.js version">

CryptoMCP requires Node.js 18 or later. Running it on an older version causes syntax errors or missing API errors at startup.

**Fix:**

Check your current version:

```bash
node --version
```

If the output is below `v18.0.0`, install a supported version. The recommended approach is to use a version manager:

```bash
# Using nvm
nvm install 20
nvm use 20

# Using fnm
fnm install 20
fnm use 20
```

Then restart the server.

</Accordion>

<Accordion title="Port already in use">

If another process is already bound to the port CryptoMCP wants to use, you'll see:

```
Error: listen EADDRINUSE: address already in use :::3000
```

**Fix — option 1:** Change the port in your `.env` file:

```bash
PORT=3001
```

**Fix — option 2:** Find and stop the conflicting process:

```bash
# Find what's using port 3000
lsof -i :3000

# Kill it by PID
kill -9 <PID>
```

Then restart CryptoMCP.

</Accordion>

## AI Client Can't Connect

<Accordion title="Wrong server path or command in MCP config">

Each MCP client stores its server list in a configuration file. If the path to the CryptoMCP entry point is wrong, the client can't launch or reach the server.

**Fix for Claude Desktop** — open `claude_desktop_config.json` (typically at `~/Library/Application Support/Claude/claude_desktop_config.json` on macOS) and verify the entry looks like this:

```json
{
  "mcpServers": {
    "cryptomcp": {
      "command": "node",
      "args": ["/absolute/path/to/cryptomcp/dist/index.js"]
    }
  }
}
```

Make sure:
- The path is absolute, not relative
- You've run `npm run build` so `dist/index.js` actually exists
- The `node` binary is on the system PATH used by Claude Desktop (run `which node` to confirm)

After editing the config, fully quit and relaunch Claude Desktop.

</Accordion>

<Accordion title="CryptoMCP server is not running">

Your AI client may require the CryptoMCP server to be running independently before it can connect (depending on your transport mode — HTTP vs. stdio).

**Fix:**

Check whether the server process is alive:

```bash
# Look for the node process
ps aux | grep "cryptomcp"

# Or try connecting directly
curl http://localhost:3000/health
```

If nothing is running, start the server:

```bash
npm start
```

Then reconnect from your AI client.

</Accordion>

<Accordion title="Firewall or network blocking the connection">

In HTTP transport mode, a local firewall or network policy may block connections to the CryptoMCP port.

**Fix:**

- Temporarily disable your firewall to test whether it's the cause.
- If you're on a corporate network, check whether outbound connections to `localhost` are restricted.
- Switch to **stdio transport** mode if your client supports it — stdio runs in-process and avoids all network concerns entirely. See your client's MCP documentation for transport configuration details.

</Accordion>

## Tool Returns an Error

<Accordion title="Missing API key for the tool being called">

Each CryptoMCP tool maps to a specific data provider. If the required key is missing from your `.env`, the tool returns an error like:

```
Error: POLYGONSCAN_API_KEY is not configured. Add it to your .env to use this tool.
```

**Fix:**

Identify which key the tool needs using this table:

| Tool | Required Key |
|---|---|
| `get_price` | `COINGECKO_API_KEY` |
| `get_market_data` | `COINGECKO_API_KEY` |
| `list_tokens` | `COINGECKO_API_KEY` |
| `get_wallet_balance` (Ethereum) | `ETHERSCAN_API_KEY` |
| `get_wallet_balance` (Polygon) | `POLYGONSCAN_API_KEY` |
| `get_wallet_balance` (BSC) | `BSCSCAN_API_KEY` |
| `get_transaction` (Ethereum) | `ETHERSCAN_API_KEY` |
| `get_gas` | `ETHERSCAN_API_KEY` |
| `get_news` | `CRYPTOPANIC_API_KEY` |

Add the missing key to your `.env` and restart the server.

</Accordion>

<Accordion title="Invalid or malformed parameters">

If you pass a parameter in an unexpected format, the tool returns a validation error such as:

```
Error: Invalid address format. Expected a 0x-prefixed Ethereum address.
```

Common parameter mistakes:

- **Token symbols** must match CoinGecko IDs (e.g., `bitcoin`, not `BTC` or `Bitcoin`). Use `list_tokens` to find the correct ID.
- **Wallet addresses** must be checksummed or lowercase hex, prefixed with `0x`.
- **Transaction hashes** must be the full 66-character `0x`-prefixed hex string.
- **Block numbers** must be plain integers, not hex strings.

</Accordion>

<Accordion title="Rate limit hit on an upstream API">

When you exceed a provider's rate limit, the tool returns an error including how long to wait:

```
Error: Rate limit reached for Etherscan. Retry after 20 seconds. (HTTP 429)
```

**Fix:**

- Wait the indicated time and retry the query.
- Increase cache TTL values in `.env` to reduce API call frequency:
  ```bash
  CACHE_TTL_PRICES=60
  CACHE_TTL_BALANCES=300
  ```
- Configure a private RPC endpoint for the chain you're querying heaviest.
- If you're consistently hitting limits, consider upgrading to a paid provider plan.

</Accordion>

## Prices Look Stale or Wrong

<Accordion title="Cache TTL is set too high">

If `CACHE_TTL_PRICES` is set to a large value (e.g., 3600 seconds), CryptoMCP serves the same cached price for up to an hour even as the market moves.

**Fix:**

Lower the TTL in your `.env` to get fresher data:

```bash
# Refresh prices every 30 seconds
CACHE_TTL_PRICES=30
```

Restart the server after saving the change.

</Accordion>

<Accordion title="Wrong token symbol or CoinGecko ID">

CryptoMCP uses CoinGecko token IDs, not ticker symbols. For example, the correct ID for Ethereum is `ethereum`, not `ETH`. Using the wrong ID either returns data for a different token or triggers a "token not found" error.

**Fix:**

Use the `list_tokens` tool to look up the correct CoinGecko ID before querying:

```
list_tokens({ query: "matic" })
```

The result includes the canonical ID, symbol, and name so you can confirm you have the right one.

</Accordion>

## Wallet Balance Shows 0

<Accordion title="Wrong chain selected">

Each blockchain is siloed — a wallet that holds tokens on Polygon will show a zero balance when queried against Ethereum, and vice versa. Make sure you're specifying the correct `chain` parameter for the network where the tokens actually live.

**Fix:**

Pass the explicit chain when calling `get_wallet_balance`:

```
get_wallet_balance({
  address: "0xYourWalletAddress",
  chain: "polygon"
})
```

Supported chain values: `ethereum`, `polygon`, `bsc`.

</Accordion>

<Accordion title="Contract address provided instead of wallet address">

Token contract addresses and wallet addresses are both 42-character hex strings starting with `0x`, which makes them easy to confuse. Querying a contract address for a balance returns 0 because contracts don't hold balances in the same way user wallets do.

**Fix:**

Double-check that the address you're querying belongs to a wallet (externally owned account), not a token contract. You can verify this on the relevant block explorer:

- Etherscan: [etherscan.io](https://etherscan.io) — paste the address in the search bar and check whether the page says "Address" or "Contract"
- Polygonscan, BscScan: same process on their respective sites

If you meant to look up token balances held by a specific contract (e.g., a multisig), use `get_defi_pool` or `get_transaction` instead, depending on your goal.

</Accordion>

## Quick Diagnostic Checklist

Run through this list whenever CryptoMCP behaves unexpectedly:

1. Confirm `.env` exists in the project root and contains real API key values (not placeholder text).
2. Verify Node.js version is 18 or later: `node --version`.
3. Check that the server process is running: `ps aux | grep cryptomcp`.
4. Confirm the port is not blocked and matches what your MCP client config points to.
5. Check the server log output for specific error messages.
6. Verify any address or transaction hash parameters are correctly formatted.
7. Confirm you're using the CoinGecko token ID (e.g., `ethereum`), not a ticker symbol (e.g., `ETH`).
8. Confirm you're querying the correct chain for the wallet or transaction you're looking up.
9. If data looks stale, check your `CACHE_TTL_*` settings and consider lowering them.
10. Test the failing API key directly in your browser (e.g., `https://api.coingecko.com/api/v3/ping?x_cg_demo_api_key=YOUR_KEY`) to verify it's valid.

<Tip>
Set `LOG_LEVEL=debug` in your `.env` and restart the server before reproducing your issue. Debug logging prints the full request and response for every upstream API call, making it much faster to identify exactly where something is going wrong. Remember to switch back to `LOG_LEVEL=info` once you're done debugging.
</Tip>
